١ السوكيت (Socket) — الأنبوب بين الجهازين

الفكرة أولًا (قبل أي كود)

السوكيت هو قناة بايتات بين برنامجين عبر الشبكة. تخيّل أنبوب ماء بين بيتك وبيت جارك: تدفع ماءً من طرفك فيخرج من طرفه. لكن الأنبوب لا يعرف أين تنتهي رسالة وأين تبدأ أخرى — كل ما تراه هو تيّار بايتات متّصل.

هذه حقيقة أساسية في TCP: هو تيّار (stream) وليس رسائل. لذلك قد:

  • تُرسل رسالة واحدة، فتصل على دفعتين صغيرتين.
  • تُرسل رسالتين، فتصلان ملتصقتين في قراءة واحدة.

⚠️ الخطأ الشائع عند المبتدئين

الاعتقاد أن recv() تُعيد الرسالة كاملة. لا تفعل ذلك أبدًا. الحل هو إضافة "طبقة تأطير" (Framing) نتّفق فيها على شكل الرسالة: نكتب طولها في البداية.

1) فتح السوكيت — server.py

import socket

srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)  # TCP
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind((config.HOST, config.PORT))    # نحجز منفذًا
srv.listen(32)                        # نستمع
conn, addr = srv.accept()               # ننتظر اتصالًا واحدًا

🔎 سِنْتاكس غريب — فكّه

  • socket.AF_INET: عائلة العنوان = IPv4 (عناوين مثل 127.0.0.1).
  • socket.SOCK_STREAM: نوع السوكيت = TCP (موثوق ومُرتَّب). لو كتبت SOCK_DGRAM صار UDP.
  • SO_REUSEADDR: يسمح بإعادة استخدام المنفذ فورًا بعد إغلاق السيرفر (يمنع خطأ «Address already in use»).
  • listen(32): الرقم = حجم طابور الانتظار (عدد الاتصالات التي لم تُقبل بعد)، وليس عدد العملاء.
  • srv.accept() تُرجع زوجًا (conn, addr) — سِنْتاكس «تفكيك المجموعة» (tuple unpacking): يوضع ناتج الدالة في متغيّرين معًا.

2) خدمة عدّة عملاء في الوقت نفسه — Threads

import threading

conn, addr = srv.accept()
threading.Thread(
    target=_handle_connection, args=(conn, hub), daemon=True
).start()

🔎 سِنْتاكس غريب — فكّه

  • Thread(target=..., args=(...)): نشغّل الدالة في خيط تنفيذ منفصل حتى لا يتجمّد السيرفر عند انتظار عميل.
  • args=(conn, hub): لاحظ الفاصلة — لأن بايثون لا تعتبر (x) مجموعة، بل (x,) بفاصلة.
  • daemon=True: خيط «خَدوم» يُقتل تلقائيًا عند خروج البرنامج الرئيسي، فلا يعلّق التطبيق.

3) طبقة التأطير — protocol.py

كل رسالة نغلّفها في «صندوق» رأسُه ثابت الحجم، وفيه الطول:

┌────────┬─────────┬──────┬───────┬──────────┬───────────────┐ │ magic │ version │ type │ flags │ reserved │ length │ ← الرأس (12 بايت) │ "SCP1" │ 1 byte │ 1 B │ 1 B │ 1 B │ 4 bytes │ ├────────┴─────────┴──────┴───────┴──────────┴───────────────┤ │ payload (بطول length) │ ← الحمولة └─────────────────────────────────────────────────────────────┘
HEADER = struct.Struct(">4sBBBBI")  # قالب الرأس

def pack_frame(ftype, payload=b"", flags=0):
    return HEADER.pack(MAGIC, VERSION, ftype, flags, 0, len(payload)) + payload

🔎 سِنْتاكس غريب — struct وb""

  • b"SCP1": نص بايتات (bytes) وليس نصًا عاديًا. البادئة b تعني: هذه بيانات خام، لا حروف يونيكود.
  • struct.Struct(">4sBBBBI"): قالب لتحويل أرقام إلى بايتات ثنائية. تفكيك الرموز:
    الرمزالمعنى
    >ترتيب البايتات Big-endian (الشبكة تستخدمه دائمًا).
    4sنص (bytes) بطول 4 بايت.
    Bعدد صحيح غير سالب بطول 1 بايت (0..255).
    Iعدد صحيح غير سالب بطول 4 بايت.
    إذن الرأس = 4 + 1 + 1 + 1 + 1 + 4 = 12 بايت بالضبط.
  • HEADER.pack(...) يحوّل الأرقام إلى بايتات جاهزة للإرسال. وعكسها HEADER.unpack(bytes) تُرجع مجموعة قيم.

4) قراءة الطول أولًا، ثم القراءة بالضبط — transports.py

def _recv_exact(self, n):
    buf = b""
    while len(buf) < n:                 # TCP قد يجزّئ القراءة
        chunk = self.sock.recv(n - len(buf))
        if not chunk:
            raise ConnectionError("انقطع اتصال TCP")
        buf += chunk
    return buf

def recv_frame(self):
    header = self._recv_exact(protocol.HEADER.size)   # اقرأ 12 بايت الرأس
    length = protocol.HEADER.unpack(header)[-1]     # آخر قيمة = الطول
    payload = self._recv_exact(length) if length else b""
    return header + payload

🔎 سِنْتاكس غريب — فكّه

  • buf = b"" ثم buf += chunk: نبني المُخزن تدريجيًا (bytes غير قابلة للتعديل، لذا إعادة الإسناد بـ +=).
  • recv(n - len(buf)): نطلب فقط ما تبقّى لا المزيد — حتى لا نسرق بايتات من الرسالة التالية.
  • if not chunk: في بايثون، المجموعة الفارغة b"" تُعتبر خطأ (False). لذا not chunk تعني «الاتصال أُغلق».
  • unpack(header)[-1]: الفهرس -1 = العنصر الأخير من المجموعة (وهو الطول هنا).
  • X if شرط else Y: تعبير شرطي في سطر واحد (قيمة طولها صفر تعني لا حمولة).
  • HEADER.size: خاصية تُعطي حجم القالب = 12، فلا نكتب الرقم يدويًا.

💡 الخلاصة — السوكيت

الأنبوب لا يحفظ حدود الرسائل. الحلّ: رأس بطول ثابت + الطول في المقدّمة + حلقة قراءة حتى تكتمل. هذا بالضبط ما تفعله كل البروتوكولات الحقيقية (HTTP, TLS, WebSocket…).

٢ تشفير AES-CBC — الأقفال المربوطة بسلسلة

ثابتة واحدة تشرح كل شيء

AES يقفل كتلة واحدة فقط حجمها 16 بايت. رسالتك أطول من ذلك، فنقسّمها إلى كتل. «وضع التشغيل» (Mode) هو القاعدة التي نحكم بها كيف نربط الكتل ونشفّرها. سيرة المشروع التعليمية: ECB ← CBC ← CTR ← GCM.

1) لا بد أن يكون الطول مضاعفًا لـ 16 — الحشو (PKCS#7)

BLOCK = 16

def pad(data):
    n = BLOCK - (len(data) % BLOCK)      # كم بايت ينقص؟
    return data + bytes([n]) * n         # نكرر قيمة n، n مرات

def unpad(data):
    n = data[-1]                        # آخر بايت = عدد الحشو
    return data[:-n]

🔎 سِنْتاكس غريب — فكّه

  • data + bytes([n]) * n: bytes([n]) يحوّل رقمًا واحدًا إلى بايت واحد. ثم * n = تكرار البايت n مرّات.
  • مثال عملي: النص "hello" طوله 5. إذن n = 16 - (5 % 16) = 11. النتيجة: نُضيف 11 بايت قيمة كل منها 0x0b (أي الرقم 11). يصبح الطول 16.
  • data[:-n]: تقطيع (slicing) يعني «من البداية حتى قبل آخر n بايت» — نحذف الحشو عند الفك.

2) عملية XOR — أساس كل الأوضاع

XOR (أو الحصرية) على مستوى البت: الناتج 1 فقط إذا اختلف البتّان. هي «متماثلة» — نفس العملية تُشفّر وتفكّ (a ^ b ^ b = a).

def xor(a, b):
    return bytes(x ^ y for x, y in zip(a, b))

🔎 سِنْتاكس غريب — فكّه

  • ^: عملية XOR على البتات بين رقمين.
  • for x, y in zip(a, b): zip تدمج مجموعتين عنصرًا بعنصر: (a[0],b[0]), (a[1],b[1])…
  • الكامل bytes(... for ...) هو تعبير مولّد (generator expression) — يبني البايتات واحدًا واحدًا دون قائمة وسيطة.

3) المشكلة: ECB يكشف الأنماط 🔴

في ECB كل كتلة تُشفّر بمفردها. النتيجة: نفس النص = نفس المشفّر دائمًا. هذا سبب ظهور الصور الشهيرة كصور ظلّية عند تشفيرها بـ ECB.

def ecb_encrypt(key, plaintext):
    data = pad(plaintext)
    return b"".join(
        _enc_block(key, data[i:i+BLOCK]) for i in range(0, len(data), BLOCK)
    )

🔎 سِنْتاكس غريب — فكّه

  • data[i:i+BLOCK]: نقطع 16 بايت تبدأ من الموضع i.
  • range(0, len(data), BLOCK): من 0 إلى الطول بـ خطوة 16 → مواضع الكتل (0, 16, 32…).
  • b"".join(...): يلصق كل الكتل المشفّرة في قيمة bytes واحدة.

4) الحل: CBC يربط كل كتلة بالسابقة 🟡

قبل تشفير كل كتلة، ندمجها بـ XOR مع الكتلة المشفّرة السابقة. أما الكتلة الأولى فتندمج مع IV (قيمة عشوائية). هكذا يختلف كل مشفّر حتى لو تكرّر النص.

CBC تشفير: P1 ──XOR──► [AES] ──► C1 ──┐ ▲ │ IV ▼ P2 ──XOR──► [AES] ──► C2 ──┐ ▲ │ C1 ▼ P3 ──XOR──► [AES] ──► C3 ▲ C2 P = النص الأصلي، C = المشفّر، [AES] = محرّك التشفير
def cbc_encrypt(key, plaintext, iv):
    data = pad(plaintext)
    out = bytearray()
    prev = iv
    for i in range(0, len(data), BLOCK):
        block = xor(data[i:i+BLOCK], prev)   # اربط بالسابق
        prev = _enc_block(key, block)        # شفّر → يصبح "السابق"
        out += prev
    return bytes(out)

def cbc_decrypt(key, ciphertext, iv):
    out = bytearray()
    prev = iv
    for i in range(0, len(ciphertext), BLOCK):
        block = ciphertext[i:i+BLOCK]
        out += xor(_dec_block(key, block), prev)  # فكّ ثم XOR مع السابق
        prev = block
    return unpad(bytes(out))

🔎 سِنْتاكس غريب — فكّه

  • out = bytearray(): مثل bytes لكن قابلة للتعديل، لذا out += ... يعمل بكفاءة.
  • prev = iv: متغيّر «الكتلة السابقة»، نحدّثه في كل دورة.
  • في الفكّ: الترتيب معكوس (فكّ ثم XOR)، وprev = block يحفظ المشفّر الأصلي (لا المفكوك).
  • _enc_block البادئة _: اصطلاح في بايثون يعني «دالة داخلية، لا تُستدعى من خارج الملف».

5) IV — أهمّ قاعدة أمان

iv = os.urandom(16)                                 # عشوائي لكل رسالة
payload = iv + aes_modes.cbc_encrypt(key, plaintext, iv)   # نُرسل IV معها

⚠️ لماذا IV عشوائي دائمًا؟

IV ليس سرًّا (يمكن إرساله مع الرسالة)، لكنه يجب ألا يتكرّر أبدًا مع نفس المفتاح. لو أعيد استخدام نفس (مفتاح/IV)، يُكشف النص. معيار NIST SP 800-38A نصّ صراحةً أن IV في CBC يجب أن يكون غير متوقّع (unpredictable) — أي عشوائي من مولّد آمن مثل os.urandom.
المرجع: NIST SP 800-38A §5.3 وما بعدها.

🔎 سِنْتاكس غريب — os.urandom(16)

تُرجع 16 بايت عشوائية من مولّد أرقام آمن تشفيريًا (يصلح للمفاتيح). لا تستخدم random العادية هنا أبدًا — فهي قابلة للتنبؤ.

💡 الخلاصة — AES-CBC

نقفل 16 بايت في كل مرة، ونربط كل كتلة بسابقتها عبر XOR. تغيير بايت واحد يُفسد كل الكتل بعده. IV عشوائي لكل رسالة وغير سري.

٣ WebSocket — النافذة التي يفتحها المتصفح

لماذا نحتاجه أصلًا؟

المتصفح لا يُسمح له بفتح سوكيت TCP خام (لأسباب أمنية: يمنع صفحات الويب من مهاجمة أي خدمة في الجهاز). لكن يُسمح له بفتح WebSocket: وهو يبدأ كطلب HTTP عادي، ثم «يُرقّى» إلى قناة ثنائية الاتجاه دائمة.

🧭 خطوات المصافحة (RFC 6455)

  1. المتصفح يرسل GET عاديًا مع ترويسة Sec-WebSocket-Key: <عشوائي>.
  2. السيرفر يرد 101 Switching Protocols مع Sec-WebSocket-Accept محسوبة.
  3. بعدها يتحوّل الاتصال إلى إطارات ثنائية ثنائية الاتجاه (لا مزيد من HTTP).

1) حساب الرد — websocket.py

GUID = "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"   # ثابت من RFC

def accept_key(key):
    digest = hashlib.sha1((key + GUID).encode()).digest()
    return base64.b64encode(digest).decode()

🔎 سِنْتاكس غريب — فكّه

  • (key + GUID).encode(): نلصق مفتاح المتصفح مع GUID السرّي، ثم نحوّله إلى بايتات (encode).
  • hashlib.sha1(...).digest(): بصمة SHA-1 خام بصيغة بايتات (20 بايت).
  • base64.b64encode(...).decode(): نحوّل البايتات إلى نص Base64 (حروف مقروءة).
  • هذا الثابت GUID موجود في RFC 6455 ولا يتغيّر — يمنع خداع الوسطاء.

2) الإطارات — أهمّ فرق: التقنيع (Masking)

كل رسالة تُرسل كـ «إطار». الإطار يبدأ ببايتين:

البايت 1: FIN(1) | RSV(3) | opcode(4) البايت 2: MASK(1) | length(7) FIN = 1 يعني "هذا آخر جزء" opcode = 1 نص / 2 ثنائي / 8 إغلاق / 9 ping / 10 pong MASK = 1 يعني "الحمولة مُقنّعة" (إلزامي من المتصفح، ممنوع من السيرفر) length = أقل من 126 = الطول الحقيقي 126 = الطول في البايتين التاليتين 127 = الطول في الثمانية التالية
def send(self, opcode, payload=b""):
    header = bytearray([0x80 | opcode])  # 0x80 = FIN
    n = len(payload)
    if n < 126:
        header.append(n)
    elif n < 65536:
        header.append(126)
        header += struct.pack(">H", n)
    else:
        header.append(127)
        header += struct.pack(">Q", n)
    self.sock.sendall(bytes(header) + payload)

🔎 سِنْتاكس غريب — فكّه

  • 0x80: صيغة ست عشرية للعدد 128 (وحدته العليا = بت FIN).
  • 0x80 | opcode: أو البتّي يدمج البتات: نضع FIN في الأعلى والـ opcode في الأسفل.
  • bytearray([0x80 | opcode]): ننشئ إطارًا قابلاً للتوسيع ثم header.append(n).
  • struct.pack(">H", n): H = عدد 2 بايت. و>Q = عدد 8 بايت.

3) الاستقبال + فك التقنيع + التجزئة

b1, b2 = recv_exact(self.sock, 2)
fin     = b1 & 0x80    # هل هو آخر جزء؟
op      = b1 & 0x0F    # النوع
masked  = b2 & 0x80    # هل مُقنّع؟
length  = b2 & 0x7F    # الطول
...
if mask:
    data = bytes(c ^ mask[i % 4] for i, c in enumerate(data))
if op == OP_PING:
    self.send(OP_PONG, data)
    continue
payload += data
if fin:
    return opcode, payload

🔎 سِنْتاكس غريب — فكّه

  • b1 & 0x80 (و البتّي): يبقي البت الأعلى فقط → 1 إذا كانت FIN مضبوطة.
  • b1 & 0x0F: يبقي البتات الأربع الدنيا فقط → رقم الـ opcode.
  • b2 & 0x7F: يحذف بت التقنيع ويبقي الطول (7 بتات = حتى 127).
  • c ^ mask[i % 4]: التقنيع XOR بمفتاح من 4 بايت يتكرّر. i % 4 يعيد الموضع 0..3.
  • for i, c in enumerate(data): enumerate تعطي (الموضع، العنصر) معًا.
  • continue: نتخطّى بقيّة الحلقة (بعد ردّ pong) ونعود للقراءة.

⚠️ التقنيع ليس تشفيرًا!

مفتاح التقنيع يسافر مع الإطار في الوضوح. الغرض منه فقط منع «تسميم الكاش» عبر الوسطاء (cache poisoning)، لا سرّية. لهذا نحتاج تشفيرنا الخاص فوق WebSocket.
المرجع: RFC 6455 §5.3 — «كل إطار من العميل إلى السيرفر يجب أن يكون مُقنّعًا، والعكس لا.»

4) التجريد: نفس الشيء للمتصفح وبايثون — transports.py

class WSTransport:
    def recv_frame(self): return self.ws.recv_binary()
    def send_frame(self, data): self.ws.send_binary(data)

💡 فكرة معمارية مهمة

لدينا واجهتان متشابهتان: RawTransport (TCP خام) وWSTransport (WebSocket). منطق الدردشة لا يعرف من أيّهما — يرى فقط recv_frame/send_frame. هذا يسمّى تجريد الطبقة، وهو سرّ نظافة المشروع.

٤ HMAC — خاتم الشمع الذي يكشف التعديل

الفرق الجوهري: HMAC ليس تشفيرًا

التشفير يخفي النص. HMAC لا يخفيه — النص يبقى مقروءًا. وظيفته ضمان السلامة (لم يُعدَّل) والمصادقة (المرسل يملك المفتاح المشترك).

المفهومالوظيفةهل يخفي النص؟هل يكشف التعديل؟
التشفير (AES)السرّيةنعملا
HMACالسلامة والمصادقةلانعم

لماذا لا نستخدم hash(key + message) ببساطة؟

لأنّ دوال التجزئة مثل SHA-256 مبنية على بنية Merkle–Damgård، وهي عرضة لـ هجوم امتداد الطول (Length Extension): المهاجم يستطيع إطالة رسالتك وحساب بصمة صحيحة دون معرفة المفتاح. HMAC يحلّ ذلك ببنية متداخلة (hash داخل hash).

المعادلة (RFC 2104)

HMAC(K, m) = H( (K ⊕ opad) ‖ H( (K ⊕ ipad) ‖ m ) ) H = دالة التجزئة (SHA-256 هنا) ⊕ = XOR ‖ = لصق البايتات ipad = 0x36 مكرّرة (حشوة داخلية) opad = 0x5C مكرّرة (حشوة خارجية)
BLOCK_SIZE = 64   # حجم كتلة SHA-256

def hmac_sha256(key, message):
    if len(key) > BLOCK_SIZE:
        key = _hash(key)                         # 1) جزّئ المفتاح الطويل
    key = key.ljust(BLOCK_SIZE, b"\x00")       # 2) اكمله بالأصفار

    ipad = bytes(b ^ 0x36 for b in key)      # 3) الحشوتان
    opad = bytes(b ^ 0x5C for b in key)

    inner = _hash(ipad + message)                # 4) التجزئة الداخلية
    return _hash(opad + inner)                   # 5) التجزئة الخارجية

🔎 سِنْتاكس غريب — فكّه

  • key.ljust(64, b"\x00"): يُكمل المفتاح على اليسار بالأصفار حتى 64 بايت.
  • b ^ 0x36 for b in key: نطبّق XOR على كل بايت من المفتاح مع الثابت. _hash = hashlib.sha256(...).digest().
  • البنية المتداخلة: الناتج الأول inner يدخل في التجزئة الثانية مع opad — وهذا ما يقتل هجوم امتداد الطول.
  • 0x36 و0x5C: ثابتان اختِيرا لتباعدهما الكبير في البتات (Hamming distance).

التحقق — ولا نقارن بـ == أبدًا!

def hmac_verify(key, message, tag):
    expected = hmac_sha256(key, message)
    import hmac as _std
    return _std.compare_digest(expected, tag)   # زمن ثابت!

🚨 هجوم التوقيت (Timing Attack)

لو استخدمت ==، فبايثون يقارن بايتًا بايتًا ويتوقّف عند أول اختلاف. يقيس المهاجم زمن الاستجابة ليعرف كم بايتًا كان صحيحًا، ويكتشف البصمة تدريجيًا. compare_digest يقارن في زمن ثابت بغضّ النظر عن موضع الاختلاف.

🔎 سِنْتاكس غريب — import hmac as _std

نستورد وحدة بايثون القياسية hmac ونُعطها اسمًا مستعارًا _std لأنّ اسم ملفنا هو أيضًا hmac. البادئة _ تعني «مؤقّت/داخلي». (نستفيد فقط من compare_digest؛ الحساب نفسه مكتوب من الصفر أعلاه.)

دمج HMAC مع التشفير — «Encrypt-then-MAC»

# عند الإرسال: شفّر أولًا، ثم احسب HMAC على النص المشفّر
if integrity:
    payload = payload + hmac_impl.hmac_sha256(keys["mac"], payload)
    flags |= F_MAC

# عند الاستقبال: تحقّق أولًا، ثم افكّ
if flags & F_MAC:
    body, tag = payload[:-32], payload[-32:]
    if not hmac_impl.hmac_verify(keys["mac"], body, tag):
        raise ValueError("HMAC: فشل التحقق — رُفضت البيانات المعدّلة!")

🔎 سِنْتاكس غريب — فكّه

  • payload[:-32] = كل شيء عدا آخر 32 بايت (لأن بصمة SHA-256 = 32 بايت).
  • payload[-32:] = آخر 32 بايت فقط (البصمة المرسلة).
  • flags |= F_MAC: ضبط بت العلم (bit flag) ليعرف المستقبل أن هناك بصمة.

💡 لماذا هذا الترتيب بالذات؟

«Encrypt-then-MAC» هو الأقوى: نتحقّق من السلامة قبل أن نمرّر أي شيء لمفكّك التشفير، فلا يستطيع المهاجم حتّى إرسال بيانات عشوائية للفك. ولا ننسى فصل المفاتيح: مفتاح للتشفير ومفتاح آخر للـ MAC (crypto/kdf.py).

⚠️ تنبيه تعليمي

الكود هنا مكتوب للتعلم فقط، غير مُدقّق أمنيًا. في الإنتاج استخدم مكتبات معتمدة (مثل AES-GCM المدمج).

٥ كيف تتّصل الأجزاء الأربعة معًا

[سوكيت TCP] ──┐ ├──► [طبقة التأطير: magic|len|payload] ──┐ [WebSocket] ──┘ (نعرف حدود كل رسالة) │ ▼ ┌───────────────────────────────────────────┐ │ المصافحة (hub.py): │ │ ECDH P-256 → سرّ مشترك │ │ │ │ │ ▼ │ │ HKDF → مفتاحان: enc + mac │ └───────────────────────────────────────────┘ │ ▼ [تشفير AES-CBC: IV + ciphertext] ← السرّية │ ▼ [HMAC: Encrypt-then-MAC] ← السلامة │ ▼ إرسال الإطار على الشبكة

عند الإرسال ترتيب الطبقات: تأطير → تشفير → (بصمة) → إرسال. وعند الاستقبال العكس تمامًا: قراءة الطول → التحقّق من البصمة → فكّ التشفير.

💡 جملة واحدة تحفظها

السوكيت/WebSocket = الطريق. التأطير = علبة مرقّمة. AES-CBC = القفل. HMAC = خاتم الشمع.
